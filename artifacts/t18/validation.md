# T18 · 实施与验证记录

记录日期：2026-11-12（北京时间）。规则确认与设计见 [progression-rules.md](progression-rules.md)。

> 2026-11-12 策略修正：T17 测量工具的稳健/激进词条策略原先在同组候选中退化为选第一项，已修正并补回归测试。本卡主结论使用 `first` 策略，不受影响；涉及稳健/激进的旧对照只代表选路差异，不能单独证明词条偏好收益。

## 1. 已确认规则

| 决策 | 采用值 |
|---|---|
| 等级上限 | 境界 1/2/3 分别为 3/6/10 级；旧档境界 4+ 按 10 级保留 |
| 突破门槛 | 境界 1→2 需 3 级；2→3 需 6 级；不再开放境界 4 |
| 突破费用 | 境界 2 为解锁声望 ×0.5；境界 3 为 ×0.75；破境丹 1 颗可替代，但必须满足等级门槛 |
| 等级与值守 | 等级只影响战斗；境界影响战斗、值守（每阶 +1%）和后续等级上限 |
| 旧档 | 超过当前阶段上限的等级/境界保留，不截断；可按门槛突破继续培养 |
| 招募/突破 | 招募只负责首次获得；已拥有角色使用独立“境界突破”命令 |

## 2. 实现范围

- `backend/app/domain/progression.py`：等级上限、等级费用校验、突破门槛与费用、旧档超限处理。
- `backend/app/domain/recruit.py`：只处理首次招募；已拥有返回培养提示。
- `backend/app/domain/craft.py`：破境丹与突破命令共用等级门槛；失败不扣材料。
- `backend/app/domain/training.py`：只读培养预览，复用 `combatant`、`upgrade_cost`、`breakthrough_cost` 和值守速率。
- `backend/app/api/disciples.py`：新增 `GET .../training` 与 `POST .../breakthrough`；升级/突破沿用 revision CAS 与先补算后提交。
- `backend/app/models/api.py`：新增 `TrainingStats`、`TrainingStep`、`TrainingPreview`、`BreakthroughResponse`。
- `frontend/src/components/game/DiscipleTraining.vue`：当前属性、等级上限、升级/突破费用、限制原因、旧档提示、值守影响。
- `frontend/src/views/CodexPanel.vue`：接入服务端预览；移除前端费用公式；招募页已拥有角色改为“前往培养”；升级/突破拆成独立动作。
- `frontend/src/stores/game.ts`、`api/client.ts`：预览加载、突破命令、失联后同步最新状态。
- `tools/measure_battles.py`：新增 `--suite t18`，合法档位 1/1、3/1、6/2、10/3，并与 T17 重叠档位对照。

没有修改技能、敌人、奖励、战斗公式或 T20 内容；同一等级/境界的战斗属性与 T17 一致。

- T17 的 6/1 在新规则下属于旧档超限对照，不再作为目标档位。

## 6. 用户人工检查清单

- [ ] 桌面与 390px：培养区是否完整显示当前属性、等级上限、费用、限制原因。
- [ ] 资源不足、已达上限、未达突破等级三种原因是否可区分。
- [ ] 境界突破成功后，等级不变、境界提升、按钮和下一等级状态刷新。
- [ ] 已拥有角色在招募页是否只显示“前往培养”，不再显示“提升境界”。
- [ ] 出征中的弟子：升级/突破按钮是否禁用并说明原因。
- [ ] 值守中的弟子突破后，值守产出是否按新速率显示；旧时段是否未被重算。
- [ ] 旧档超限等级/境界是否保留并显示说明，没有被截断。
- [ ] 键盘关闭弹窗、长文案、等待/错误反馈是否正常。

## 7. 已知限制

- T18 不改变战斗数值，因此 10/3 仍然过易；末期压力留待 T20。
- 培养界面只显示单个弟子的个人属性与个人值守速率，不显示全队总战力预测。
- 等级上限/突破比例目前是 `progression.py` 常量；若后续需要配置化，必须先确定单一来源，再迁移。
- 未新增批量培养、经验条、技能树、装备或专武。
