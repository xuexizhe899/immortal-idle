## 1. 现状核对（基于 46f8c8f 的实际代码）

### 1.1 候选如何生成

`run_engine.roll_choices`：按 `choices_per_step` 循环，每个候选独立抽类型（`battle` / `elite`，精英概率 20%），随后：

```python
kind = "boss" if is_boss else "elite" if rng.randint(1, 100) <= mode["elite_chance"] else "battle"
nodes.append(RunNode(kind=kind, enemy=f"{kind}_{step}",
                     power=enemy_power(step, mode, kind),
                     reward=node_reward(kind, mode, step)))
```

`enemy` 字段是 `f"{kind}_{step}"`，只由类型和层数决定；`power` 与 `reward` 同理。

### 1.2 等价候选的实际比例

同层两个候选只有三种组合：

| 组合 | 概率 | 结果 |
|---|---|---|
| 都是 battle | 0.8² = 64% | **完全等价**：编成、强度、奖励全同 |
| 都是 elite | 0.2² = 4% | **完全等价** |
| 一 battle 一 elite | 2×0.8×0.2 = 32% | 有差异 |

非首领层共 19 层，其中约 **68%（约 13 层）是假选择**。首领层只有 1 个候选，不存在选择。

这与建卡时的描述一致，T20/T21 未改动此处。

### 1.3 已有编成变体被浪费

`config/modes/tower.json` 已经准备了多组编成：

- `encounter_variants.battle`：5 组，每组 3 人（石甲灵卫×2+弓卫、竹隐剑客+石甲+弓卫、赤炉刀卫+石甲+弓卫……）
- `encounter_variants.elite`：5 组，3–4 人
- `encounter_variants.boss`：1 组，3 人

`encounter_roster(mode, kind, step)` 用 `step * len(variants) // node_count` 取索引，**只与层数有关**。同层两个候选因为 `step` 相同，必然取到同一组编成。

也就是说：差异化的素材已经存在，缺的是"逐候选独立取变体"。这让方案 A 的成本比新建一套编成低得多。

### 1.3 差异是否被玩家看见

`RunView.vue` 当前展示 `kind` 对应的文案与奖励数字。两个同类候选的奖励数字完全相同，玩家看到的是"两个一样的选项"，只能凭颜色或位置选。

### 1.4 一局的决策与点击

| 环节 | 次数 | 是否含决策 |
|---|---|---|
| 选路 | 19–20 | 68% 无有效决策 |
| 词条三选一 | 约 19 | 有 |
| 战报播放 / 跳过 | 19–20 | 无（可跳过） |
| 结算 | 1 | 无 |

**结论**：点击量的大头在"无决策价值的选路"和"战报播放"，而不是词条选择。

## 3. 最小方案（方案 A）

**只做候选差异化，不新增节点类型。**

### 3.1 候选携带真实编成

`RunNode` 增加 `enemies: list[str]`，在生成候选时逐候选抽取：

- 每个候选从该类型的 `encounter_variants` 中独立抽一组编成，而不是按类型共用。
- `power` 改为由编成的实际总战力计算，不再只看类型。
- `reward` 按 `power` 相对基线的比例缩放（强度 ×1.15 ≈ 奖励 ×1.1），保持"高风险高回报"。

这样同类型的两个候选也会有不同敌人、不同强度和不同奖励，**假选择消失**。

### 3.2 候选展示真实信息

页面展示：该候选的敌人名称与数量、总战力、可见奖励、类型标签。不展示未生成的后续路线。

### 3.3 战报与选路合并为一屏

战报结果作为选路页顶部的结果条（伤害、承伤、掉落），不单独占一屏；保留"查看完整战报"的展开入口。

**这是点击精简的主要来源**，不删任何决策。

## 6. 资源对照

当前每层奖励（`node_reward`，`scale = 1 + step × 0.1`）：

| 类型 | 修为 | 灵石 | 灵草 |
|---|---|---|---|
| battle | 10 | 5 | 1 |
| elite | 20 | 10 | 2 |
| boss | 50 | 25 | 5 |

改造后奖励按编成强度缩放，**总量目标控制在当前 ±10% 以内**，不因"差异化"额外发奖励。具体做法：以当前类型的基准值为 1.0，编成强度相对基准的比值作为系数，上限 1.3、下限 0.85。

失败结算与保底不变。

## 7. 两个状态的选择示例

### 示例 A：满血、有护盾技能的队伍（第 8 层）

- 候选 1：石甲灵卫 ×2 + 流云弓卫，可见奖励 修为 10.4 / 灵石 5.2
- 候选 2：竹隐剑客 + 赤炉刀卫 + 流云弓卫，可见奖励 修为 11.6 / 灵石 5.8

选择：候选 2。理由：队伍有诸葛亮护盾，能吃掉弓卫的单点爆发；赤炉刀卫的降防会拖慢战斗，但多 12% 奖励且气血余量足够。

### 示例 B：残血、核心输出已倒下的队伍（第 8 层）

- 同一对候选。
- 选择：候选 1。理由：竹隐剑客的双刺会同时打两名低血成员，当前阵型经不起；宁可少拿 12% 奖励，先用石甲的低攻把盾养起来。

**关键**：两个示例的候选完全相同，选择随队伍状态翻转；判定依据是存活人数与气血余量，不是文案。

编成名称取自现有 `encounter_variants.battle`；奖励与战力为示意值，实施后按实际计算校准。

## 8. 存储、RNG 与兼容

| 项 | 方案 |
|---|---|
| 存储 | `RunNode.enemies: list[str] = []`；旧局为空时回退到 `encounter_roster(mode, kind, step)`，不重置出征 |
| RNG | 每个候选多消费 1 次（抽编成索引）；顺序固定为「类型 → 编成 → 下一个候选」，游标随候选一起落档 |
| 候选固定 | 候选生成即落档；进入节点使用 `node.enemies`，不重新抽取 |
| 接口 | 响应增加 `enemies`、`power`、`reward` 的候选级字段；契约走 Pydantic → OpenAPI → TypeScript |
| 旧局 | 缺 `enemies` 时按旧逻辑生成敌人，行为与现在一致；不删除、不转换用户数据 |
| 测量 | 统计一局的请求次数（选路 + 词条 + 结算）与战报展开次数；时长由用户试玩记录，不由执行者推断 |

## 9. 不新增恢复 / 整备 / 机缘的理由

1. 卡片要求"若仅靠现有普通/精英差异即可成立，应优先采用更小方案"。候选差异化已能消除 68% 的假选择。
2. 恢复节点会改变层数语义（是否占层、是否给词条、失败层数奖励），牵连 `settle_run`、`tower_floor` 与旧局兼容；在 T21 修复尚未落地时引入，风险叠加。
3. 整备与机缘需要新的可见信息结构与随机结果定义，属于独立设计，不宜与"消除假选择"混在一期。

若后续确认需要恢复，建议单独立项，按"占层、不给词条、只恢复存活成员"实现。
