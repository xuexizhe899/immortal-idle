# P0 v2 · 已攻克宗门单场论道

2026-11-14（v2）。状态：方案待确认，未改代码、未跑测试、未部署。
取代 2026-11-14 初版。初版的「塔重问」「挑战词缀」「两组候选」「额外难度层」全部移出本期。

## 1. 问题定义（按复核意见收紧）

**问题：缺少指定建设材料的主动来源。**

用户实玩：问道塔一阶通关、一级主殿开放的三座外宗全部攻克后，不知道还能做什么。

需要纠正初版的三处不准确表述：

| 初版说法 | 纠正 |
|---|---|
| 「一次性内容打完，只剩等挂机」 | 问道塔**现在就能重复挑战并领奖**（`settle_run` 的 tower 分支没有已通关限发），一级三宗首胜合计 90 灵石（`conquest.py:82`，`30 × level`）。不是只能等 40 小时，还需核对实际库存与消耗 |
| 「砍掉塔复战后灵石只剩挂机」 | 取消的是**新增的「重问」入口**，现有问道塔仍能重复赚灵石。四种奖励的理由是让论道自身形成完整建设循环、减少来回切换玩法 |
| 「没有埋点，所以拿不到实际库存」 | 当前库存可以从存档读取；缺的是**过去每笔消费的完整流水** |

真正的、可核对的缺口：现有塔掉落（`ling_cao / yun_mu / han_tie / jiao_gu / xuan_jing / jiu_ye`）与一级外宗产材（`han_tie / qing_shi / ling_cao`）**都不产灵木、赤铜**；青石也只有御守驻守来源。它们有挂机与值守来源，**不是资源死锁**，是缺少「缺什么就去打哪里」的主动途径。

## 2. 目标与边界

**首版只做一个完整闭环**：已攻克宗门开放单场论道 → 固定基础材料奖励 → 出发前展示本场奖励与设施缺口 → 用独立测试档验证升级后能继续推进。

沿用 AGENTS 已锁定约束：不新增货币、不新增模式系统、不新增关卡数量、不做真实时间限时事件；服务端独占资源与奖励计算；随机只走本局确定性源；消耗命令带 `revision` / CAS / 并发锁；变更产出前先补算旧区间；旧档缺新字段按原逻辑运行。

**本期不做**：词缀、两组候选、短塔配置、额外难度倍率层、塔复战入口、全站美术重做。

## 3. 玩法规则

### 3.1 入口

| 项 | 规则 |
|---|---|
| 解锁 | 该外宗 `conquered = true` |
| 消耗 | 2 点行动力（复用现有征讨消耗） |
| 内容 | **单场宗主战（3v1）**，复用目标宗门已有的宗主战斗快照 |
| 难度 | 不加倍率层。前三座宗门虽同为一级，但宗主模板、属性、技能本就不同，`ensure_sects` 已生成差异（`conquest.py:61`）。若实测某类明显过难，再考虑论道专用配置 |
| 队伍 | 沿用现有征讨校验：3–6 名随行、每场 3 名上阵 |
| 次数 | 不设次数上限，行动力（0.5/h、12h 封顶）为天然闸门 |

单场论道**不改变** `conquered`、驻守编制、宗门身份；不重复发首胜奖励；不占用塔阶进度。

### 3.2 奖励（固定表，独立核算）

三座一级外宗按风格分工，让「缺哪种材料就打哪座」成立：

| 外宗风格 | 论道奖励 |
|---|---|
| 丹修 | **灵木 8、灵石 11** |
| 御守 | **青石 14、灵石 11** |
| 剑修 | **赤铜 4、灵石 10** |

- 合计 **灵石 32、灵木 8、青石 14、赤铜 4**，正好覆盖「二级主殿 + 二级问道塔」从零库存的总需求（按 `config/facilities.json` 的 `hall.costs[0]` 与 `tower.costs[0]` 相加）。
- **声望、专材不进入首版奖励表**，不套用首胜 `sect.loot` 倍率，避免一级论道每场给出 36–54 灵石、72–108 声望、3–5 份专材而挤压驻守价值。
- 奖励表按 `style` 配置化，不随玩家库存动态变化（避免智能掉落破坏可重放）。
- 奖励进 `pending_loot`，沿用本局结算流程，不提前入永久行囊。

### 3.3 出发前展示

- 展示本场固定奖励。
- 展示「距离目标设施还缺多少」：**复用 `FacilitiesSection.vue` 现有的 `held(id)` 缺口展示逻辑**，前端算 `需要 8、持有 3、还差 5` 属于纯展示，不是扣资源或决定升级结果；服务端负责费用、可升级判断与实际扣款。
- `held(id)` 已统一读取 `resources`（灵石等）与 `inventory`（材料），不需要新增服务端 `cost + inventory` 响应字段。
- **目标设施选择是本地展示偏好**（组件局部状态或 localStorage），不成为论道出发的必填参数，不写入 `state_json`。

## 4. 状态、快照与结算

### 4.1 新增字段（最小）

`ActiveRun` 增加两个带默认值的字段，旧局反序列化后走原逻辑：

| 字段 | 用途 |
|---|---|
| `is_retrial: bool = False` | 当前规模下区分首胜征讨与论道 |
| `retrial_reward: dict[str, float] = {}` | **出发时固化的论道奖励快照** |

宗主战斗输入**不新增字段**：现有 `start_run` 已 `deepcopy(mode)`，`party_snapshot.mode["sect"]` 就是固化后的 `NpcSect`（含 `leader`、`arena_teams`），`arena()` 也已是 `NpcSect.model_validate(run.party_snapshot.mode["sect"])`。

### 4.2 关键规则

1. **出发时**固化论道奖励与宗主战斗输入。
2. **结算读取本局奖励快照**，不重新读取最新配置；出征途中改配置不漂移。
3. **胜利发论道奖励，失败为零**；不改变攻克状态、不发首胜奖励。
4. 离岗、回岗、伤势沿用既有规则：`restore_after_run(run.return_posts)`；失败时按 `not victory and disciple.id in run.deployed` 给参战者一层伤势，胜利不产生伤势。
5. 每局气血按现有 `hp = {unit.id: unit.health ...}` 独立初始化为上限，不跨局继承。

### 4.3 独立结算分支

`settle_run` 的 `if run.sect_id:` 现在同时管「标 conquered + 发首胜奖」，直接复用会重复发或不发。改为：

```
if run.sect_id:
    if run.is_retrial:
        loot = dict(run.retrial_reward) if victory else {}
        # 不碰 target.conquered，不读 sect.loot
    else:
        loot = dict(run.pending_loot) if victory and not target.conquered else {}
        if victory: target.conquered = True
```

`start_run` 的 `:287` 校验改为「已攻克宗门仅允许论道入口」，普通征讨仍拒绝。

### 4.4 流程时序（无候选，闭环）

1. 论道页选目标宗门与队伍 → 出发请求带 `sect_id`、`party_ids`、当前 `revision`、`is_retrial = true`。
2. 服务端校验已攻克、行动力 ≥ 2、队伍合法 → **扣行动力、锁队（busy / 离岗记入 `return_posts`）、固化宗主快照与 `retrial_reward`**，一次 CAS 保存。
3. 单场宗主战 → 结算按 4.3 分支发奖、回岗、按需记伤势。
4. 刷新、切页、往返宗门：快照与本局状态都在档里，**不重抽、不重扣、不重复发奖**；请求结果不确定只查询最新状态，不自动重发。

失败口径明确且不矛盾：**论道单场失败 = 零奖励**；塔失败按现有 `defeat_loot` 折算此前胜场所得（两个不同入口）。初版把两者混成一句是错的。

## 5. 经济验证（两类案例，独立测试档）

### 5.1 共同假设（必须写进验证记录）

| 项 | 假设 |
|---|---|
| 队伍 | 3 名上阵、3–6 名随行；不占用值守/驻守满编假设另记 |
| 胜负 | 三次论道全胜；失败分支单独测（零奖励 + 参战者伤势 + 行动力已扣） |
| 气血 | 每局按上限独立初始化，三次之间不继承 |
| 伤势与疗伤 | 全胜时**疗伤成本 0**；失败场景按每人一层伤势，记疗伤丹数量或自然消伤时长 |
| 行动力 | 每次 2 点 × 3 = 6 点；`0.5/h × 12h` 封顶 = 单次上线可得 6 点 |
| 起始库存 | 案例 A 为 0；案例 B 按真实存档 |

### 5.2 案例 A · 零建设资源压力测试

从零库存出发，只靠三次论道（丹修 / 御守 / 剑修各一次），检验：
- 是否存在**必须等待现实时间**才能升级的卡点；
- 是否能升二级主殿**且**升二级问道塔；
- 升完后**能否实际进入二阶问道塔**（塔阶解锁还需「一阶通关」，需在记录中确认）。

三次奖励合计须覆盖 32 / 8 / 14 / 4；若实测不足或溢出，按数据调整固定数值，不改敌人或培养收益来掩盖。

### 5.3 案例 B · 正常游玩流水

用独立测试档记录通关、培养、炼制、设施升级的实际收支，检验奖励是否**过多**：
- 每笔收入（塔重复、论道、挂机、驻守）与支出（升级、炼制、培养、疗伤）逐步记账；
- 记录到达「升完主殿与塔设施」时的实际行动力、耗时、点击次数、疗伤消耗；
- 与 5.1 的 6 点行动力 / 三次论道目标对照，说明偏差原因。

零库存只作为压力测试，**不能替代正常经济验证**；当前库存可从存档读取，缺的是历史每笔消费记录，案例 B 的流水正好补上这份缺口。

## 6. 验证方式（实施后）

1. 后端：奖励快照固化与配置热改不漂移、行动力只扣一次、失败零奖励、CAS 冲突与重复点击、`conquered` 不变、驻守不受影响、旧局 `is_retrial` 缺省兼容、离岗回岗与伤势。

4. 实测：按第 5 节两类案例在**隔离测试档**执行，不访问或修改用户真实存档。
5. 人工：桌面与 390px 的论道奖励展示、设施缺口、等待/失败、键盘与减少动态效果，由用户确认，不由执行者宣称视觉验收。
