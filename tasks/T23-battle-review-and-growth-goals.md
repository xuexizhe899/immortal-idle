# T23 · 失败复盘与成长目标回流

2026-11-12（北京时间）。状态：代码已实现；用户人工实玩与浏览器视觉验收待执行。实际字段与限制见 `artifacts/t23/review-and-goals.md`。

## 一、目标与边界

在现有问道塔循环中，让玩家能说明“这次发生了什么、我准备调整什么、下一次如何判断调整有用”，并把编队、培养、丹药与专武连接回真实战斗。深入现有选择，不增加新的内容体量或第二套任务系统。

依赖 T18 培养、T19 定向丹药与专武，以及 T20–T22 最终实际落地的敌人、战斗与奖励规则。开工须核对代码、配置与证据，不以任务卡勾选替代事实。前置任务尚未完成时，先记录依赖差异；不能照计划稿伪造已经存在的敌人、事件或收益。

不新增货币、每日任务、成就、成长轴、模式、自动奖励或胜率预测；不更改既有解锁门槛、费用、掉落、伤势、战斗判定或培养上限。T24 再处理全站前端美术优化，本期只做完成决策闭环所需的信息结构、文案和操作连接，不生图、不批量换素材。

## 二、开工先核对原始素材

阅读 `AGENTS.md`、`ARCHITECTURE.md`，以及 T17 规则账本和 T18–T22 的最终规则、实现与交付记录；历史样本只作参照，不能替代当前版本结果。

重点核对以下实际入口：

- 战斗事件与终止：`backend/app/domain/battle.py`、`run_engine.py`、`backend/app/models/battle.py`、`save.py`；确认事件顺序、实际治疗、护盾增加/吸收、倒下与回合耗尽能支持哪些指标。
- 结算与存档：`backend/app/api/run.py`、`api/state.py`、`models/api.py`、`repositories/saves.py`；确认何时清除 `active_run`、如何保存结算摘要、revision 与恢复语义。
- 培养/物品/专武：`domain/progression.py`、`training.py`、`items.py`、`weapons.py` 及对应接口/配置；复用真实可用性与预览规则。
- 玩家现有入口：`frontend/src/views/CityView.vue` 的 `currentGoal` / `followGoal`、`RunView.vue`、`SectPanel.vue`、`CodexPanel.vue`、`CraftPanel.vue`、`PreparePanel.vue`，以及 `stores/game.ts`、`rendering/battlePlayback.ts`。
- 目前 `last_battle` 位于进行中的出征里，`lastRun` 是前端内存结果；开工确认此状态是否已变化，不能假定结算后刷新仍能复盘。首页已有目标浮签，优先审查、替换或复用它。

建立首局、卡关、通关三段实玩证据：使用专用新档/隔离数据，记录真实操作路径、战前快照、关键事件与玩家当时的问题。观察由用户人工试玩反馈，或复用其明确提供的当前版本记录；不得擅自做浏览器视觉验收。缺少某段证据时写明缺口及获取方式，不能用想象中的玩家行为补齐。

## 三、先交付规则，再实施

先产出 `artifacts/t23/review-and-goals.md`。规则稿必须逐项说明数据来源、计算定义、缺失时行为、跳转条件、保存上限和验证方式，再进入实现。涉及新增存档/契约语义的选择先给具体方案及影响，按已授权范围推进。

文档主表按以下链路组织，不按页面堆功能：

| 链路 | 必须回答 |
|---|---|
| 真事件 | 哪个战报、回合、稳定行动序号和目标状态支持这条信息？ |
| 事实指标 | 统计本场还是整次出征，原始值、取整与并列规则是什么？ |
| 玩家问题 | 玩家是在问伤害不足、保护未及时生效、成员先倒下，还是不知道收益用途？ |
| 相关操作 | 可以去哪个现有入口查看什么，是否有资源/等级/出征限制？ |
| 再次验证 | 下一次用什么可观察变化检查自己的判断，哪些变量已经改变而不能直接归因？ |

首局、卡关、通关各至少完成一条有真实来源的链路；不能把固定的“升级/买药”推荐列表当作失败分析。

## 四、复盘事实与建议分开

### 事实口径

1. 明确“本场首位倒下者”，按战报稳定顺序确定；本场开始前已经倒下的人不算本场新倒下，未出现倒下则直接说明。只有保存了完整来源才可扩展为“本次出征首位倒下”，不能拿最后一场代替全局。
2. 区分全员倒下、回合耗尽与胜利。回合耗尽可以仍有存活成员，不能将剩余气血伪造为归零，也不能把到达第 20 层等同于战胜首领。
3. 展示本场结束的存活敌人、剩余气血与必要状态，读取服务端离场状态，不用当前 catalog 重建历史数值。
4. “关键行动”先采用可解释的事实筛选，例如导致倒下的行动、实际最大气血损失的行动；明确排序与并列处理，保留事件定位。数量有限，不把所有行动标成关键，也不宣称某次行动是唯一失败原因。
5. 治疗使用实际恢复量，护盾区分施加增量与实际吸收；只在原始数据足够时计算比例。没有请求治疗量就不推算溢出，没有状态来源就不宣称护盾提前到期。缺少数据标“未记录”，不能填 0。
6. 名字、技能、敌人身份与数值优先来自本局快照/战报；摘要保存必要的历史身份，不能因改配置而把旧战斗说成另一场。

### 启发建议

- 事实写“第 3 轮关羽先倒下”，建议可写“可查看编队顺序、保护技能与当前伤势”，不能直接写“防御不够，升级即可获胜”。
- 治疗低、护盾吸收低、羁绊触发少，不自动等于角色无用；同时考虑战斗长度、可用目标、伤势和敌人行为，避免把统计量当因果证明。
- 可提示比较一项调整前后的结果，优先保留其余条件；敌人、种子、路线、词条或投入不同就注明不可作严格对照。不为复盘重新结算战斗、不替玩家预测必胜，不增加一键最优阵容或自动培养。

## 五、结算后保留什么

规则稿先定摘要模型和明确上限，再修改存档。建议每档仅保留**最近一次已结算出征的 1 份小摘要**：终止结果、到达/完成口径、实际战利品、相关成员身份、最后一战的必要事实和最多 3 条关键行动摘录；双方单位各最多 6 个，不保留所有节点战报、动画帧或无限历史列表。

- 记录清楚摘要覆盖的是最后一战还是整次出征。需要跨场累计的指标在服务端逐场维护有限统计，不从不存在的历史补算。
- 在同一次结算 CAS 中保存摘要、结算收益与清理本局状态；不能只写 localStorage 或前端 `lastRun`。摘要读取、重播或跳转绝不发奖。
- 规则稿写出最终字段、条数/字符串限制和预计序列化大小；实施后核对实际体积，不能只说“轻量”。新结算覆盖旧摘要，不随出征次数增长。
- 旧档缺摘要使用空值，界面说明“暂无可用复盘”；不补发奖励、不猜测历史首胜。导入、导出、复制与快照恢复沿用现有存档语义，恢复后显示该档该时间点的摘要。
- 首次通关依据真实首领胜利/完成结算条件。若当前永久记录只有最高到达层数，明确补充最小事实字段或“未记录”的兼容方案；不能把旧档到达 20 层直接推断为已通关或从未通关。

## 六、现有目标与操作回流

目标是当前状态的解释与导航，不是可领奖的任务。服务端根据真实条件产生目标/行动可用性，复用培养预览、物品库存/服用限制、专武解锁/归属与出征规则；前端只渲染响应和导航，不另写一套成长费用、门槛或目标完成公式。

- 审查首页现有浮签、宗门总览与相关面板，明确一个目标来源与优先顺序。进行中或待结算的出征优先指向恢复/结算，不被培养建议覆盖；不要再新增独立任务面板和重复徽标。
- “去编队”打开当前存档的实际队伍；“去培养”选中对应弟子并读取当前预览；“去用药”区分库存已有、需要炼制、次数已满与不适用；“去专武”区分未解锁、材料不足、已拥有未装备、已装备。
- 导航不自动扣资源、服药、锻造、换装或发命令。需要变更时仍由用户在原入口操作，沿用 revision、并发锁与错误反馈。
- 出征仍锁定本局队伍和输入；不可培养/用药/换装时显示真实原因，不为“去调整”新增中途解锁捷径。当前状态变化后重新读取可用性，旧摘要不充当今天仍可操作的证明。
- 首次体验通过现有招募、值守、编队和一次真实战斗理解一种实际配合，例如保护支持输出或降防帮助后手；不强制锁定唯一角色答案，不改新档资源与敌人数值来制造演示。
- 阶段目标连接已有培养、药品和专武条件，具体引用 T18–T22 的最终规则，不在本卡另定新等级/塔层门槛。资源不足时说明缺什么及已存在的来源，不凭空给等待时间或新增任务奖励。
- 本版通关后明确“本版问道塔已完成”，保留已开放功能和可选的其他角色组合尝试，不暗示存在未开放章节，也不把无终点刷满所有角色写成必须完成的主线。

## 七、实施落点与顺序

1. 核对前置结果与三段实玩证据，完成规则稿和差异清单；先确定哪些问题能由现有事件回答。
2. 在领域内生成有限事实摘要与目标规则，结算编排负责原子持久化；`models/save.py`、`models/api.py` 是契约来源。确有独立职责时才新增领域模块，不创建一整套任务引擎。
3. 重新导出 OpenAPI 并生成前端类型。store 镜像摘要/目标并处理切档；展示转换进入 `presentation/`，复盘区域和目标回流只接入现有页面/业务组件。
4. 核对原始事件 → 摘要 → 显示 → 操作条件 → 再验证路径，同步相关 README 和规则文档。页面美术、全站排版与素材重制留到 T24。

## 八、验证与完成标准

按执行时 `AGENTS.md` 和用户最新指令，仅做与实际改动相关的检查；本卡生成阶段不运行测试、不实现代码。后续涉及摘要/结算/存档时选择对应后端测试，前端状态与展示变动补对应测试及类型检查构建；契约变动重新生成。视觉检查由用户人工进行，不能宣称自动视觉验收。

- [ ] 用户在卡关后能根据一条真实事实说清一个问题，自主选择一项调整，并说明下一次观察什么；不只复述“等级不足”。
- [ ] 用户能说清当前一次投入给谁、消耗什么、预期改变什么；结果未改善时仍可核对原判断，不被必胜承诺误导。
- [ ] 首局能理解一次真实配合；首次通关后知道本版已完成以及哪些其他组合属于自选尝试。
- [x] 覆盖本场无倒下、开场已有倒下、空/缺失战报、关键事件并列、全员倒下与回合耗尽；缺数据不伪造统计和因果。
- [x] 摘要有明确数量与大小边界；结算后刷新仍能读到，重复结算、回看与跳转不能再发收益，响应丢失只查最新状态。
- [x] 旧档缺字段、导入导出、恢复快照、刷新与切档后事实归属正确；不同存档的摘要、选中弟子和目标不串用。
- [x] 编队/培养/药品/专武跳转对应现有入口；导航不自动消费，出征锁定仍由原规则处理。
- [x] 目标复用首页浮签和现有入口，不新增奖励、门槛、任务系统或游戏状态真值。
- [x] 交付 `artifacts/t23/review-and-goals.md`、实际实现范围、必要验证结果、用户人工检查清单与已知数据限制；首局/卡关/通关人工问答仍待补。
