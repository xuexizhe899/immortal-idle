# T21 · 局内词条与构筑深化

2026-11-12（北京时间）。状态：方向已确认，待 T20 收口后核对现状、细化规则并实施。依赖 T17 测量基线、T18 培养、T19 个人物品与 T20 敌人优化的实际交付结果。

## 一、目标与玩家体验

让同一套弟子在不同敌人、剩余气血和已选道法下，产生有理由的不同选择。一局内的道法应逐步形成打法，并在真实行动中体现作用。

本期重做现有选择的价值，优先使用已有 20 条词条和三个协同组。数量、特效数量和属性总量不作为完成标准。保留问道塔 20 层、1–6 人自动战斗、最多 20 轮及现有局外成长体系；选路节奏交给 T22，系统复盘与目标回流交给 T23，全站视觉改版放在其后。

用户已确认本期方向和执行顺序。本卡中的构筑举例是设计候选，具体机制、系数、抽取和叠加规则须通过方案定案；已授权范围内的例行实现选择自主完成，需要改既定规则的地方集中列清，避免逐文件重复索取许可。

## 二、开工前核对原始材料

先读根目录 `AGENTS.md`、`ARCHITECTURE.md`、`DESIGN.md`、`ART_DIRECTION.md`，以及 T17–T20 任务与实际产物。不能只依据任务卡中的历史现状开展实现。

| 材料 | 核对内容 |
|---|---|
| `config/affixes/*.json` | 逐条核对名字、真实效果、组别、权重与用途；找出同义、严格强弱和名字误导 |
| `backend/app/domain/affix.py`、`run_engine.py` | 候选如何生成、何时选择、如何影响实际参战单位；重复、权重、气血重算及快照来源 |
| `domain/battle.py`、`models/battle.py`、`config/skills/`、`config/bonds/` | 已有动作、条件、目标与羁绊修饰的实际能力，明确可复用和确需扩展部分 |
| T20 正式敌人定义与编成 | 哪些敌人威胁构筑、哪类选择能应对、代价是什么；美术储备不视为已投放敌人 |
| `tools/measure_battles.py` 及 T17–T20 报告 | 实际策略选择逻辑、投入口径、种子、输入指纹与战报，而非只读汇总胜率 |
| 当前页面与用户试玩记录 | 玩家选词条时能看到的敌情、队伍状态、已选道法、解释与操作成本 |

编卡时的现状：`连击`、`破军`、`裂甲` 分别是攻击 +3%/+4%/+6%；抽取先选一个组，再从该组产生三项。测量工具按组偏好选词条，因此面对同组候选时不能有效比较具体选择。开工时重新核对这些事实；T20 后重新保存对照，不把 T17 历史清关率当作当前难度。

## 三、先交付构筑设计与规则表

产出 `artifacts/t21/affix-design.md`，至少包含：

1. 现有词条盘点：每条的实际用途、重叠或误导、保留/重做/改名/停用建议，以及旧 ID、旧局与展示兼容处理。
2. 三种候选打法的完整因果链：参与弟子与技能 → 核心道法 → 配合道法 → 适用敌情 → 风险与替代选择。可先验证“破甲爆发、护盾进攻、恢复持久”，若与 T20 实际机制不合，应说明并调整。
3. 各条的条件、适用对象、效果、持续时间、上限、重复处理和来源名称；主动、被动、羁绊、个人物品、局内道法之间的叠加与执行顺序。
4. 候选与成长规则：同组/跨组、核心获得时机、重复候选、已选项再出现、组权重、最高叠层与无可选项行为。是否改当前抽取规则须明确，不能边实现边默改。
5. 至少三个具体选择案例：同一候选面对不同队伍气血、敌情或已选道法时为何改变选择；展示收益与代价，避免只有一项在所有情形中严格更优。
6. 一条构筑从早段到首领的形成过程，以及核心未出现时仍可采用的替代打法；不以必须抽中特定词条作为唯一通路。

规则表先给有限、可验证的效果。优先复用已有条件和技能修饰；确需新机制时列最小字段、触发时机、目标限制及回归范围，再按确认的方案实施。不得引入任意脚本执行、逐角色硬编码、无限触发或递归行动链。

## 四、实现与状态约束

- 词条定义进入 `config/affixes/` 并由服务端模型、配置加载与校验统一解释；计算落在现有领域层。前端只展示实际定义与事件，不另算生效结果。
- 每项效果必须有准确文案。“连击”只有在实际具有相应行为时才保留这个含义；若决定保留纯属性效果，名称与描述应如实说明。
- 区分战前属性、入场状态、主动修饰与行动条件的生效阶段，防止每次重建参战单位重复叠加。改变气血上限时明确当前气血如何变化，不能借反复选择、刷新或回放获得额外治疗。
- 出发时固化词条定义、相关技能与解释所需的数据；当前局只读自己的快照。新版本配置不能覆盖旧局输入，旧快照缺新字段时须有明确兼容行为，不重置用户出征或资源。
- 抽取只消耗服务端现有确定性随机源，记录游标消费顺序。读说明、预览、测量展示、重播及跳过不消费玩法 RNG；刷新不能重新抽取候选。
- 选择沿用 revision/CAS、命令并发锁与原子保存。重复点击不重复获得；响应不确定只查询，不自动重发。
- 界面展示当前候选、已选构筑及必要的触发说明。选择后在真实行动或状态中能识别来源；无法从现有事件证明的触发不能补造日志。
- 本期界面改动以支持判断为限，复用现有组件、图标和战斗演出。复杂复盘面板、全站布局、主城背景与整套美术重做不混入本期。

## 六、实施与测量顺序

1. 保存 T20 完成后的固定种子、合法培养档位、丹药/专武投入和队伍快照，明确对照输入。既有未确认的生图或界面素材不影响规则测量。
2. 完成词条与构筑方案，先验证覆盖三种打法的最小代表集合，再处理其余旧项；正式候选里不能遗留未实现或描述不符的效果。
3. 在离线工具中从同一决策前状态分别选择不同候选，保持其他输入和后续策略一致，记录实际伤害、有效治疗、护盾吸收、先后手、生存和回合变化。工具可克隆状态做对照，正式预览不提前执行或泄露未来结果。
4. 更新策略：根据玩家当时可见信息比较具体候选；分别记录选路策略与词条策略的影响，不能把“都取首项”包装成不同构筑策略。策略不读取未来路线或未展示候选。
5. 完成真实事件展示与用户人工检查材料，记录有效选择、无效选择和仍被某一最优解支配的案例。

产出 `artifacts/t21/balance-report.md`、带输入指纹的对照数据及 `validation.md`。不设未经实测的统一胜率目标，也不通过改敌人或回收培养收益掩盖词条问题；若确需跨期调参，单列影响与方案。

## 七、验收

- [ ] 每条正式词条的名称、解释、条件和真实效果一致，未实现项不进入候选。
- [ ] 三种打法均有可复现的形成样本、适用敌情与代价；功能位和已有羁绊能参与，不要求绑定唯一角色名单。
- [ ] 至少三个同候选的对照案例证明合理选择随状态改变，报告能从实际行动解释差异。
- [ ] 同组内具体选择得到测量；构筑不能只凭组标签、面板战力或总属性判定成立。
- [ ] 重复、上限、叠加顺序、回合边界、无效目标及气血变化有明确规则和必要回归。
- [ ] 刷新恢复、CAS、响应丢失、配置变化、旧局、导入导出及快照恢复保持正确；选择与重播不重复结算。
- [ ] 按实际改动执行相关后端/工具/前端检查；配置改动运行配置校验，涉及随机运行 RNG 检查，契约改动先导出再生成前端类型，前端代码改动运行构建。命令遵从执行时最新 AGENTS 与用户指令，不把历史结果写作本次通过。
- [ ] 提供桌面与 390px 的用户人工检查清单：候选长文案、已有道法、等待/失败、键盘及减少动态效果；视觉由用户确认，不宣称自动验收。
- [ ] 交付设计、实际实现清单、对照、测试结果和限制，为 T22 留下可复用基线；本卡中的未执行项保持未勾选。

## 八、美术与后续阶段

本期默认复用现有素材，词条标识优先用本地 SVG。确需复杂位图时列明用途、模型、当前任务调用上限和试稿；历史敌人或专武额度不自动转移。现有技术栈足以承载本期目标，换引擎或数据库须有实测问题及独立方案。

T22 继续选路与单局节奏，T23 补失败复盘与成长目标，之后进入用户已确认的前端美术优化阶段。T21 只建立支持构筑判断的必要展示，不提前实施全站改版。
