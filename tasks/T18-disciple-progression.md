# T18 · 弟子培养优化

2026-11-12（北京时间）。状态：已确认并实施；采用境界 1/2/3 等级上限 3/6/10、突破费用 0.5×/0.75×、等级不影响值守。规则与验证见 `artifacts/t18/`。

## 一、目标与已确认方向

用户确认本期优化弟子培养。让玩家在弟子详情内看清“当前能力、培养代价、提升结果、下一目标”，培养收益能对应真实战斗和值守，不靠总战力数字代替解释。

本卡授权方向不等于具体成长公式已定。先提交带数值示例的方案，再按确认结果实现；等级上限、境界门槛、费用曲线和旧成长处理不得静默更改。

## 二、现状与范围

- `backend/app/domain/progression.py`：升级消耗当前等级 ×20 修为、×10 灵石；等级成长常量为 10%，境界为 5%。具体属性作用以 T17 账本为准。
- `backend/app/domain/recruit.py`：重复招募消耗原声望价格的一半，提升境界；当前不是独立突破流程。
- `backend/app/domain/craft.py`：破境丹可直接为指定弟子加境界。T18 设计必须考虑此入口，不能只限制重复招募而留出旁路。
- 培养入口集中在 `frontend/src/views/CodexPanel.vue`；当前个人信息、招募、编队和培养混在同一面板。
- 本期保留现有 16 人、品质、倾向和技能身份。丹药实物化与专武交给 T19。

## 三、建议规则方案（执行前确认）

1. 保留等级与境界两条成长轴：等级表达持续投入，境界表达阶段目标。优先改善现有两条轴，不先增加资质随机、洗点、技能树或碎片升星。
2. 列出各阶段等级/境界边界、单次与累计费用、属性增量及值守影响。用 T17 目标层段验证投入回报，说明是否保留现有公式。
3. 将“首次招募”和“境界提升”在文案与操作上分开。是否继续使用声望、增加等级前置或突破材料，必须给出具体方案和现有资源用途对照，确认后实施。
4. 培养预览应由服务端复用真实规则计算，展示当前与下一阶属性、费用、限制原因。前端不得复制成长公式形成第二套真值。
5. 默认先实现单次培养。批量培养只有在确有重复操作问题且费用/边界已明确时加入，不顺带增加一键养成系统。
6. 已有等级、境界、资源和永久加成不回收。若设置新上限，要明确超过上限的旧角色如何保留和展示；不得强行截断或通过补发反复获利。

## 四、可靠性与接口

- 使用现有命令编排：当前 revision → 补算旧区间 → 校验培养与资源 → 原子保存。失败不扣费、不部分升级。
- 出征中的弟子不可培养；同时校验 `busy` 与实际出征名单。进行中的战斗快照不因局外培养变化。
- 值守中的弟子若可培养，先结算旧速率，再记录新速率事件；确认等级和境界各自对值守的真实影响，不能漏结算或重复结算。
- 请求结果不确定时仅查询最新状态，不自动重发。CAS 冲突不覆盖其他操作。
- 新增字段遵循 Pydantic → OpenAPI → TypeScript，兼容已有宗门数据、导入导出与快照恢复；T16 的旧出征例外不能套用为删除培养数据的理由。
